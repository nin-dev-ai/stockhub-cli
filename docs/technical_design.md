# Technical design

## Runtime architecture

```text
Browser → Vite/React UI (:5173) → /api proxy → OpenBB API (:6900) → data providers
```

The shell scripts in the repository root install, start, and stop the local services. [`app/vite.config.ts`](../app/vite.config.ts) proxies `/api` to the OpenBB API. [`app/src/lib/api.ts`](../app/src/lib/api.ts) centralizes frontend requests to `/api/v1`, request parameters, response extraction, and error handling.

## Frontend map

| Area | Source | Responsibility |
| --- | --- | --- |
| Application shell | `app/src/App.tsx` | Maps function codes to screens and renders the active tab |
| Function registry and command parser | `app/src/lib/functions.ts` | Defines codes, symbol requirements, and command syntax |
| Function screens | `app/src/functions/` | Render market and ticker data |
| API client | `app/src/lib/api.ts` | Typed fetchers and API errors |
| Signal rules | `app/src/lib/signals.ts` | Classifies metrics and computes INTEL verdicts |
| Workspace state | `app/src/store/workspaceStore.ts` | The one open screen (`tabs` holds a single entry; `openTab` replaces it) and the active symbol, persisted with Zustand (version 1 migrates old multi-tab state to the screen that was showing) |

React Query handles data fetching and refresh intervals inside function screens. The browser calls the local Vite server, which forwards API requests to OpenBB. Most fetchers explicitly request the `yfinance` provider; treasury rates use `federal_reserve`, and symbol search uses `sec`. Company news bypasses OpenBB: `fetchNewsCompany` reads Yahoo Finance's RSS feed, then Google News if Yahoo is empty or fails, and `app/src/lib/news.ts` parses the XML. The local server's routes are one table in [`app/stockhub.config.ts`](../app/stockhub.config.ts), used by both `server.proxy` and `preview.proxy` in [`vite.config.ts`](../app/vite.config.ts), so `npm run dev` and `npm run preview` behave alike: `/api` (OpenBB), `/rss/yahoo` and `/rss/google` (Yahoo requires a browser `User-Agent`), `/clerk`, `/ark-api`, `/ark-assets`, `/figi`, `/ibkr` (the IBKR Client Portal Gateway, `IBKR_GATEWAY_URL`, self-signed certificate accepted), and, only when configured, `/sec/data`, `/sec/www` and `/llm/v1/messages`. `readEnv` reads the shell and an uncommitted `app/.env` (shell wins); `defines` passes only on/off flags and non-secret values to the browser; `featureBanner` prints which optional features are on at startup. A test checks that no prefix begins another (Vite matches by prefix) and that no secret reaches the browser flags. Provider availability and credentials affect returned data. The route shapes in `api.ts` target OpenBB 4.x (`/equity/price/quote?provider=...`); OpenBB 5 serves provider-first routes, so `setup.sh` pins `openbb>=4.3,<5`. Revisit the pin and `api.ts` together when migrating.

## Quant engine (Phase 2)

The strategy engine is a UI-free TypeScript library in `app/src/quant/` that runs in the browser and is tested with Vitest.

| Module | Responsibility |
| --- | --- |
| `instruments.ts` | US-ETF/USD universe (about 40 ETFs grouped by asset class for pickers), index-to-proxy map, static exposure vectors |
| `data.ts`, `dataSource.ts` | Dividend-adjusted history via OpenBB (`adjustment=splits_and_dividends`), alignment on common dates, content-hash dataset id, quality flags, local price cache. An empty provider answer is retried once and never cached; a ticker that still fails becomes an empty, error-flagged series, and only strategies that trade or benchmark it refuse to run |
| `strategy.ts`, `rules.ts`, `catalog.ts` | Versioned JSON strategy schema, validation (no leverage, long-only), plain-English rules generated from the definition, the 21 curated strategies, and `retarget`, which swaps ETFs in a definition (merging weights and repeated assets that land on the same ETF) to make a variant with a new id and a caveat |
| `backtest.ts` | Deterministic daily simulation: decide on data through close t, fill at close t+1 with slippage and fees, time-weighted returns separate from contributions, locked cash for DCA and reserves, decision and trade reasons |
| `metrics.ts`, `indicators.ts` | Metrics that return null with a reason when the sample is too short; indicators that cannot see the future |
| `robustness.ts` | Train/test split, rolling 3-year windows, parameter sensitivity, verdict |
| `service.ts` | `runBacktestOn` / `runBacktest`: validation, run id = hash(strategy, dataset, config, engine version), benchmark on identical cash flows, conventions and flags |
| `ranking.ts`, `useBacktests.ts` | Evidence-first ordering; progressive runs over one shared dataset |
| `portfolio.ts`, `overlap.ts` | Weight validation (long-only, sum to 100%), blending of strategy return streams, cash-flow paths; overlap by asset class and return correlation |
| `optimizer.ts` | Exhaustive 1% grid search over capped long-only weights for three objectives, binding constraints, baselines, out-of-sample refit |
| `projection.ts` | Seeded block-bootstrap or parametric simulation of terminal wealth: fan percentiles, real values, loss and goal probabilities, stress scenarios, refusal on short history |
| `jobs.ts`, `lab.ts`, `useLab.ts`, `report.ts` | Idempotent in-thread job queue with progress and cancellation (ids hash kind, input and engine version); Lab input validation and composition; calculation report and CSV export |
| `tracking.ts`, `useTracking.ts` | Portfolio ledger (no leverage, no short sales), valuation over adjusted closes, plan targets and paper rebalancing, content-addressed frozen projection snapshots, plan replay on realized returns, attribution against a snapshot, timeline alignment, reforecast |

Allocation types: `static`, `trend` (price vs SMA), `momentum`, `vol_target`, `seasonal`, `tsmom`, `risk_parity` (inverse volatility), `multi_trend` (per-asset SMA slots), `crossover` (fast vs slow SMA), `mean_reversion` (Wilder RSI with optional trend filter) and `schedule` (dated target weights in any US ticker, stocks included; each step holds until the next and the unallocated part sits in the safe ETF; used for copy-trade backtests). Every signal uses data through the decision close only. Catalog strategies only use ETFs with history from before 2005 so the shared window stays at 2004-11-18; a test enforces this.

**Spread across ETFs.** A definition may carry `spread: { from, targets: [{ ticker, weight }] }` (up to six ETFs, weights summing to 100%). `simulate` then runs one sleeve per target (`sleeveDef` replaces `from` with the target through `applyTarget`), funds each with its weight's share of the initial capital and of every contribution, and adds the sleeves; sleeves are never rebalanced against each other, and per-trade costs apply per sleeve. Because the split happens inside `simulate`, robustness, the optimizer and projections treat a spread strategy like any other. `withSpread` builds one (equal weights by default) from the ETF the strategy trades (`primaryRisky`: the risky asset, the reserve ticker or the largest equity weight of a fixed mix); multi-asset rotations have none and cannot be spread. `quant/spread.ts` adds a `spread` section to the result: each ETF's CAGR, drawdown, Sharpe and share of the gain, the sleeves' return correlation, the same rules on the original ETF alone, buy-and-hold of the same ETFs with the same split, and whether the combined worst drawdown is shallower than the best sleeve's. With one target the run equals the plain retargeted run (tested).

State for baskets, drafts and the screen-wide ETF switch (`target`, applied by `targetedStrategies`; it only swaps ETFs a strategy trades, so one that merely benchmarks against SPY is unchanged) is in `app/src/store/strategyStore.ts`. An on-screen variant is saved as a draft when it is added to the basket so the Lab and Portfolio can resolve it by id. Lab inputs in `app/src/store/labStore.ts`, and portfolios with their snapshots in `app/src/store/portfolioStore.ts` (browser storage; snapshots are append-only and re-frozen on load). Jobs run on the main thread and yield between chunks; the engine has no DOM dependency, so moving them into a Web Worker is a contained change. Run `LIVE=1 npx vitest run src/quant/live.test.ts` from `app/` to run the catalog against the local API, and `LIVE=1 npx vitest run src/quant/livePhase3.test.ts` (with the dev server on port 5173, for `/clerk`) to read Nancy Pelosi's House reports, backtest copying them with a look-ahead check, and spread the golden cross across SPY, QQQ and DIA on real prices.

**Card facts (Phase 6).** `quant/cardFacts.ts` is pure: `tradeOff` compares CAGR and worst fall with the benchmark (gaps under 0.1 point and falls within 1 point count as equal), `isYardstick` marks a static 100% benchmark holding without `entry` or `reserve` rules, `crisisFalls` takes the time-weighted worst peak-to-trough inside fixed S&P 500 crisis windows (`CRISES`; null when the run does not cover one), and `holdingToday` reads `currentTargets` and walks the rebalance decisions back to the last change (targets within 2 points count as the same) for *since* and *before*, with `nextCheckDate` giving the first weekday of the next period. Spread strategies show holdings without a switch date.

**Buy list (Phase 6).** `quant/buyList.ts`: `buyList(targets, price, amount)` floors each target notional over the latest close, the same rounding `proposeRebalance` uses from cash (a test checks they agree), and reports cost, weight, gap, leftover cash, ETFs it cannot buy and `minimum` = the largest price / target. `rebalanceTrades(..., wholeShares)` rounds paper sales and purchases down to whole shares; `Portfolio.wholeShares` records the choice made in Save Plan, and My Portfolio shows the buy list at today's value for fractional paper plans.

**Plan to-do and alerts (Phase 6).** `quant/planTodo.ts` is pure: from the portfolio, its original snapshot, the strategies re-run on current data and the price panel it lists signal switches (a change in a strategy's rebalance targets after the portfolio's last trade), drift past `DRIFT_LIMIT` = 5 points (holdings the plan no longer wants count as 0% targets), a due rebalance (the snapshot's `inputs.rebalance` period has changed since the last trade and holdings are off target) and a missed monthly contribution, each with a stable key. `useTracking.ts` exports `submitTracking`, the shared `port-refresh` job, so `components/PlanWatcher.tsx` (mounted in `App`) refreshes every saved plan on start and every 60 minutes when `planAlertStore.alerts` is on, notifies each new key once and reports its count to `titleStore`, which also takes the persona count and sets the tab title.

### Portfolio tracking

- **Snapshots.** A snapshot holds the inputs, weights, full strategy definitions and hashes, dataset id, plan targets and the projection's fan and percentiles. Its id is the hash of its content, so `verifySnapshot` detects any later edit, and it is deep-frozen in memory. Reforecasts are new snapshots that point to the original.
- **Valuation.** Value is cash plus units times the adjusted close. Paper trades are priced at the adjusted close; because adjusted histories are rescaled after each later dividend, paper lots are re-expressed in current adjusted units, which reinvests distributions like the backtester. Manual records use their units as entered, so cash dividends should be recorded as entries.
- **Attribution.** Observed value minus the original median = contribution difference (actual minus planned money in) + projection error (the plan's weights replayed on realized returns with the actual cash flows, versus the median path) + allocation difference (observed minus that replay). FX is not applicable while the universe is USD only.
- **Reforecast.** Re-runs the snapshot's strategies on current data, then projects from the current value with the plan's monthly contribution over the chosen horizon.

### Personas

`app/src/quant/personas.ts` defines presets with a source: `fund` (SEC CIK, Form 13F), `insider` (ticker plus first/last names, Form 4) or `house` (a US House member keyed by the Clerk's spelling of last name, first name and district). `fundChanges` aggregates 13F rows per CUSIP, security type and option type (names carry the share class, such as "Class A", so two classes of one issuer read apart), then diffs the latest two quarters into new / added / trimmed / sold-out trades. `normalizeInsider` maps Form 4 rows (transaction codes to short labels; zero prices become null), and `matchesInsider` filters a company's filings to the person. `fetchForm13F` and `fetchInsiderTrades` in `lib/api.ts` call OpenBB's SEC provider (`/equity/ownership/form_13f`, `/equity/ownership/insider_trading`); "No Form 4 data" becomes an empty list. Passing `start_date` to the insider endpoint returned no data in testing, so it is not used and the window is the provider default (about four months). `functions/PERS.tsx` makes one query per distinct source. Follows and added personas persist in `store/personaStore.ts` (version 2 resets the earlier congressional follows). `UNAVAILABLE_PEOPLE` and `POLITICIAN_NOTE` let the Copilot explain why senators and the President cannot be followed yet.

**House members.** `quant/congress.ts` parses the Clerk of the House's yearly index (`/public_disc/financial-pdfs/<year>FD.zip`, XML inside) into filings and keeps Periodic Transaction Reports (`FilingType` P). Electronically filed PTRs (document ids `2xxxxxxx`) have a text layer: `parsePtr` takes positioned text runs from every page (`quant/pdfText.ts`, pdf.js), finds the column titles of the transaction table, and rebuilds rows (owner, asset, ticker, asset-type code, transaction type, transaction and notification dates, amount range, description), continuing rows across page breaks and stopping at the footnote. Sub-headings drawn without a text mapping arrive with NUL characters and are recognised as labels. `ptrTrades` maps rows to `PersonaTrade` with `amount` holding the range and no value, shares or price; `filed` is the index filing date. A golden test parses a real three-page filing kept in `quant/fixtures/`. `lib/house.ts` fetches through the `/clerk` Vite proxy (the Clerk sends no CORS headers), unzips with fflate, lazy-loads pdf.js with its worker, reads a member's newest 24 reports from this year's and last year's index three at a time, and lists scanned paper filings, failures and older reports as links instead of guessing. The index is cached for 12 hours and parsed reports by document id indefinitely (a filed report never changes; an amendment gets a new id).

**Copy-trade backtest.** `quant/copyTrade.ts` turns a member's purchases and sales with a ticker into events (a sale is full unless the action says partial; exchanges and untickered assets are skipped and listed), then into a `schedule` allocation: on each date something changed the copy holds every stock bought and not fully sold in equal weights, otherwise SHY. It is run twice with `runBacktestOn` on one dataset (the persona's tickers plus SPY and SHY, from a month before the first trade): acting on the filing date (`filed`) and on the trade date (`traded`), both from the first trade date so the windows match. The lag cost is the difference in final value; the median filing delay, priced tickers, unpriced tickers and skipped assets are reported. A test asserts that the filing-date version never decides to buy a stock before its first report. `functions/personas/CopyTradePanel.tsx` renders it and publishes a summary to the Copilot context (`PersonasContext.copy`). Copy strategies are not saved as drafts: their stock histories would cut the Strategies screen's shared 2004+ window, and under two years of data is below the Lab's 60-month projection minimum. Funds are not offered because the 13F rows carry CUSIPs, not tickers.

### Lab ETF choice

`LabInputs.etf` (default SPY) and `labStrategies` apply `applyTarget(def, { SPY: etf })` to the basket before backtesting; when `LabInputs.alsoEtfs` lists more ETFs, strategies whose main ETF (`primaryRisky`) is SPY are spread across `[etf, ...alsoEtfs]` with `withSpread` (equal split, benchmark stays SPY) and the rest only get the swap; `CORE_ETFS` in `instruments.ts` lists the one-click choices and leads every ETF dropdown.

### Copilot

`app/src/copilot/` is a deterministic assistant with no network calls.

| Module | Responsibility |
| --- | --- |
| `context.ts` | Store that screens publish structured results to (open strategy and backtest, Lab inputs/weights/optimization/projection, portfolio attribution, persona buys and sells loaded on the Personas screen); the panel passes only the active screen's entry |
| `assistant.ts` | `respond(message, context)`: guardrails, intent routing, and answer builders. A `Composer` formats every figure from engine fields and records it; `verifyFigures` then rejects any number in the text that is not in those records, vetted rule/glossary text or the user's message, and `hasUnsafeCertainty` rejects promise language |
| `guardrails.ts` | Classifies the user's message only (injection, action, certainty, advice); context text is never routed as an instruction. Draft strategies' free text is not quoted |
| `drafting.ts` | Pattern-based translation of a description into the strategy schema, with assumptions, unsupported parts, validation, edits to a copy of the strategy in context, a rule-field diff, and `variantFromText` ("on QQQ", "X instead of Y") which retargets a named or open strategy |
| `labChanges.ts` | `labChangeFromText`: reads the Lab inputs the Copilot may propose (ETF, or several to spread across as `alsoEtfs`, starting amount, monthly contribution, horizon) and validates them with `validateLab` |
| `glossary.ts` | Curated definitions and alias matching |

Permission levels are fixed in PRD 6.6.1. On the Personas screen, questions about loaded trades are answered from the published rows (`personaTrades`; issuer names are registered with `Composer.data`). Lab-input requests become a `labChange` proposal; the panel's `LabChangeCard` shows current and proposed values and calls `labStore.setInputs` only on Apply. The action guard no longer refuses "plan"/"inputs" wording because those requests become proposals; edits to portfolios, weights, assumptions, ledgers, transactions and snapshots are still refused. `personaRequest` routes "follow / track / what is X trading" to a persona answer; the panel's `PersonaCard` follows through `personaStore` only on click. User drafts' names are never quoted (`curatedName`).

The UI is `app/src/components/CopilotPanel.tsx`; drafts reuse `DraftEditor` and save through `strategyStore`. **Optional LLM phrasing.** `copilot/llm.ts` lets Claude reword an answer, never decide it. `respond` still routes the message and builds the grounded answer, its figures and any action card (draft, persona, Lab change, open screen). When the dev server was started with `STOCKHUB_LLM_KEY`, `phrase` posts the user's message and the grounded answer's text (no tools, a fixed system prompt that treats both as data) to `/llm/v1/messages`; the Vite proxy forwards only that path to `STOCKHUB_LLM_URL` (default `https://api.anthropic.com`) and adds the key and API version server-side, stripping the browser's origin, referer and cookies, so the key never reaches the bundle. The reply must pass `verifyFigures` against the grounded text, the user's message and the static figures, and `hasUnsafeCertainty`; otherwise the grounded answer is kept and marked *Rule-based wording*. Refusals and withheld answers are never sent. Accepted replies replace the blocks, keep the cards and sources, and keep the grounded blocks for a *Show the computed answer* toggle. `STOCKHUB_LLM_MODEL` picks the model (default `claude-sonnet-5-5`). Without a key nothing changes and no request is made. Tested with fake model replies (faithful, invented figure, buy/sell and certainty language, server error, refusal) and in the browser against a mock Messages endpoint; not yet against the real API.

## Change points

- To add a function, register it in `functions.ts`, create its screen in `app/src/functions/`, and wire it in `App.tsx`.
- To change a data call or its response type, edit `api.ts` and the screens that consume it.
- To change INTEL interpretation, edit `signals.ts` and check how `INTEL.tsx` composes the signals.
- To change service ports or setup, inspect `app/vite.config.ts` and the root shell scripts together.

## Interactive Brokers (read-only)

`quant/ibkr.ts` normalizes the Client Portal Gateway's `/v1/api` responses: `gatewayState` (from `/iserver/auth/status`), `normalizeAccounts` (paper accounts are ids starting with D, such as DU1234567), `normalizePositions` (zero positions dropped; ticker from `ticker` or the first word of `contractDesc`) and `normalizeSummary` (net liquidation and cash). `trackable` keeps long USD `STK` positions with a price and lists the rest with a reason. `syncDrafts` compares a ledger's units with the broker's and returns sales for decreases (priced at the broker's price, or a supplied last close for a holding the broker no longer reports) followed by `transfer_in` entries for increases; a second sync with the same positions returns nothing. `lib/ibkr.ts` is the client: `assertReadOnly` allows only `GET /iserver/auth/status`, `POST /tickle`, `GET /portfolio/accounts`, `GET /portfolio/{id}/positions/{page}` and `GET /portfolio/{id}/summary`, and throws for anything else before a request is made (tested against order, reply, cancel and what-if paths). Requests time out after 8 seconds, because on macOS AirPlay Receiver holds port 5000 and hangs instead of refusing. Positions page 100 at a time. `functions/portfolio/BrokerPanel.tsx` polls the status (every 10 s until connected, then every 60 s), sends a keep-alive every 60 s while connected (the gateway drops idle sessions after about six minutes), and syncs only on a click. Broker-reported portfolios (`PortfolioMode` `broker`) are valued like manually reported ones. The UI was verified against a mock gateway returning the documented shapes; it has not been run against a real IBKR account.

## Paper orders

`quant/orders.ts` holds the rules: `proposeRebalance` (whole shares; only the plan's tickers; total = their value plus cash; sales first, purchases scaled to the cash available; a ticker with no broker price is noted, not bought), `checkOrder` (kill switch, account selected and paper, ticker on the allow-list `INSTRUMENT_BY_TICKER`, whole positive quantity, no selling more than held, market or limit with a price, resolved contract id, per-order cap, daily cap), `validateLimits`, audit entries and `spentOn` (today's submitted notional, UTC). `lib/ibkrOrders.ts` is the only code that can send orders: every function first calls `assertPaper` (paper ids start with D) and throws before any request otherwise; `submitOrder` re-runs `checkOrder`, requests `/iserver/accounts` (the gateway requires it) and posts the order; a reply prompt comes back as `{ kind: "question" }` and is answered only by `answerQuestion` from the user's click; `cancelAll` cancels the account's open, unfilled orders. `store/orderStore.ts` persists the audit log (append-only, last 5,000 entries), the kill switch and the limits. `functions/ORD.tsx` logs a blocked send as rejected without counting it toward the cap, and logs proposals, previews, submissions, IBKR questions, answers, placements, kill switch and limit changes. The Copilot can attach an *Open Paper Orders* button (`Answer.open`) but has no access to these modules. Verified end to end against a mock gateway (preview, question, answer, placed order, kill switch cancel); not yet run against a real IBKR paper account.

## Plans (Phase 4)

`quant/plan.ts` holds the plan logic as pure functions. `planRole` derives a strategy's job from its rules: a `static` mix with at least half in stock or REIT ETFs is core, any other static mix, `risk_parity` and `multi_trend` are diversifiers, every signal rule is tactical (a spread strategy takes its first sleeve's rule). `planHoldings` multiplies each strategy's current targets by its plan weight and `assetClasses` maps ETFs through the static exposure table; current targets come from `currentTargets` in `backtest.ts`, which for a spread strategy sums every ETF sleeve's latest targets (`Sleeve.targets`) instead of reading only the last merged decision, and `planTargets` (used by Paper Orders) now uses it. `checkPlan` returns ordered checks: the worst fall against `LabInputs.fallLimit`, redundancy (`isRedundant`: shared exposure at least 75% or return correlation at least 0.9; a core with a trend overlay on the same market is normal), roles, concentration over 60%, sleeves under 5%, and whether mixing reduced volatility below the weighted average of the parts. `fitCandidate` scores a candidate (fills a missing job, correlation with the plan's blended returns, robustness verdict, experimental penalty) and the worst fall with it at 25%; `suggestPlan` picks the best-evidenced core, then a diversifier and a tactical sleeve that are not redundant with a chosen sleeve, and searches weights on a 5% grid (each 10%-70%, the core at least `CORE_MIN` = 40% and never smaller than another sleeve) for the highest CAGR with a worst fall inside the limit, preferring mixes whose largest asset class (`topClassOf`, from each candidate's average exposure, cash excluded) stays under `MAX_CLASS` = 60%, the share at which the plan check warns; it uses a concentrated mix only when no spread one fits and says so, and falls back to the shallowest fall when nothing fits the limit. It returns a one-line reason per pick and the largest asset class. `defaultPlanName` names a saved plan from its fall limit (under 20% cautious, under 35% balanced, under 50% growth, else aggressive), numbering repeats. In `LAB.tsx`, opening the Allocation or Projection tab runs that job if it has no result, and Save Plan runs the projection first when needed (a `wantSave` flag opens the drawer once the job finishes). Candidates are aligned to their common dates (`alignSleeves`). `quant/useCandidates.ts` runs the catalog on the Lab's ETF choice with the scorecard settings and robustness checks, only while a panel that needs it is open; results are shared with the Strategies screen through the backtest cache. The basket limit is `MAX_BASKET` (5) and `setBasket` replaces it; the optimizer's grid step is `stepFor(n)` (1% up to three strategies, 2% for four, 5% for five) so the exhaustive search stays small. The Lab runs the backtest automatically whenever the strategies or inputs change, so the Plan tab is always live. `functions/lab/PlanView.tsx`, `BuildPlan.tsx` and `AddStrategy.tsx` are the UI; plan edits set the weight override keyed by the Lab-mapped strategy ids.

## Live SEC filings (Phase 4)

`quant/edgar.ts` parses what EDGAR publishes within days: `parseSubmissions` turns `data.sec.gov/submissions/CIK##########.json` into filings with their acceptance time (to the second), `recentLive` keeps Form 3/4/5 and Schedule 13D/G inside 120 days, de-duplicated across CIKs (one Form 4 names several owners, such as Berkshire and Buffett), newest 30; `parseForm4` reads the XML (issuer and ticker, reporting owners, role, 10b5-1 flag, each non-derivative and derivative transaction with its code, shares, price and holding afterwards, with lines of one kind on one day summed); `parseStake` reads a 13D/G (the two schedules use different tag names: the largest beneficial holding among the reporting persons, its percent of the class, the event date) as a row with `category: "stake"`. `PersonaTrade` gained `accepted`, `form` and `category`; `publicAt` and `byRecency` sort by acceptance time, else filing date, else trade date. `EDGAR_CIKS` lists each preset's firm and person CIKs, verified against the SEC (for example Huang is 1197649, not the similarly named 1106277); a fund without an entry uses its own CIK. `lib/edgar.ts` fetches through the `/sec/data` and `/sec/www` Vite proxies, which add a `User-Agent` built from `STOCKHUB_SEC_CONTACT` or, when that is unset, from the `x-stockhub-sec-contact` header the browser sends with a contact typed into Personas (`personaStore.secContact`; `secUserAgent` and `validSecContact` in `stockhub.config.ts` accept one line with an email address under 120 characters, and the proxy strips the header, cookies, origin and referer before forwarding). Without either, the proxy's `bypass` answers 404 locally, so nothing reaches the SEC; `useSecLive()` / `secLive()` decide whether the browser reads live filings. The e2e suite runs a second dev server without the contact (port 5181) to test the form. limits requests to three at a time and about seven a second across all personas, and caches parsed rows by accession (a filing never changes; 400 kept). `PERS` runs one live query per persona with SEC identities (5-minute interval), merges its rows with the quarterly ones, and replaces the provider's four-month insider query when live is on. `personaStore.seen` holds the newest acceptance time the user has seen per persona; the first look sets the baseline and leaving the screen advances it. The Copilot keeps a fund's quarterly changes apart from its live insider filings and names the newest filing time. `LIVE=1 LIVE_BASE=<dev server with the contact set> npx vitest run src/quant/liveEdgar.test.ts` checks real Berkshire and Zuckerberg filings.

**ARK daily trades.** `quant/ark.ts` and `lib/ark.ts`: `parseArkTrades` turns `arkfunds.io/api/v2/etf/trades` rows (six ETFs: ARKK, ARKQ, ARKW, ARKG, ARKF, ARKX; 30 days) into buy and sell rows with signed shares, the fund's weight in the detail, no price or value, `form: "ARK daily"` and `filed` equal to the trade date; `parseHoldingsDate` reads the date of the first row of ARK's own `ARK_INNOVATION_ETF_ARKK_HOLDINGS.csv`. The dev server proxies `/ark-api` to arkfunds.io and `/ark-assets` to assets.ark-funds.com (neither prefix may begin with the other, because Vite proxies match by prefix). `Persona.daily: "ark"` marks the persona (Cathie Wood); `PERS` refreshes the feed every 15 minutes and merges the rows; `isLiveRow` (an SEC acceptance time or `ARK daily`) keeps these rows apart from the quarterly 13F in the Copilot's summaries and in the date column. No key is needed, and the feed is unofficial, so the screen labels it. A fund family that publishes daily trades could be added the same way.

**Copilot plan proposals.** `copilot/planRequest.ts` recognises a request for a whole plan (build, make, create, suggest, propose, design, recommend a plan, or "a plan for me"; a question about what a plan is does not match) and reads the fall limit from "25% fall/drawdown/drop" or a risk word (conservative 15%, balanced 25%, aggressive 40%; limits outside 5-90% are ignored). `respond` routes it before the Lab-input route and returns a `plan_proposal` answer with `planProposal: { fallLimit }` and no numbers beyond the user's own, so it passes the figure check. Testing the catalog takes a moment, so the card (`PlanProposalCard` in `CopilotPanel.tsx`) only mounts `BuildPlan` (the Plan tab's panel, which runs `suggestPlan`) after a click; applying calls `setBasket`, sets the weight override and the fall limit, opens the Lab and keeps the previous basket, override and limit for Undo. The Copilot never sees the strategies or results itself.

**History window.** `LabInputs.lookbackYears` (null = everything) becomes `RunConfig.start` through `backtestConfig(inputs, now)` (`lookbackStart` counts back whole years from the current date); the engine already sliced the panel at `start`, so the backtest, the optimizer and the projection's bootstrap sample all use only that window. `runBacktestOn` passes `simulate` the history up to the end date and `simulate` starts money at the first date on or after `start` (`t0`), so signals see the earlier history and a window trades from its first day; the warm-up flag appears only when no earlier history exists. Robustness segments still use the windowed panel. `MIN_PROJECTION_YEARS` (5) matches the projection's 60-month minimum and drives the hint. `LabInputs.years` is the forward horizon, labelled *Look forward*. The Copilot's `labChangeFromText` reads "the last/past/previous N years", "N years of history" and "look back N years" as the window and removes that phrase before reading the horizon, so "test the last 10 years and project 5" sets both; "all/full history" sets null. Saved snapshots embed the inputs, so an older snapshot without the field is treated as all history.

**Withheld-answer guard.** An answer is withheld only when the figure check finds a number that is not in an engine result, vetted product text or the user's own message. Static text that contains a number must therefore be registered with `Composer.vetted`; the help list once was not, so every message the Copilot did not understand answered "Answer withheld". `copilot/sweep.test.ts` runs about 80 realistic messages (concepts, numbers in free text, small talk, supported requests, refusals, typos) on nine screens, and every suggested prompt, and fails if any answer is unverified; it was checked to fail with the original bug restored. When adding an answer builder with static numbers, pass them through `c.vetted` and add a phrasing to the sweep.

**Rebalancing between strategies.** `LabInputs.rebalance` (`quarterly` by default; `annual`, `monthly`, `drift5`, `none`, `daily`) and `blendOf(inputs)` (rule plus the Lab's slippage as the cost) feed `blendReturns(sleeves, weights, { rule, costBps })`. Except for `daily`, each strategy's money grows on its own and is moved back to the targets on the first trading day of each month, quarter or year, when any strategy is more than 5 points off target, or never; each rebalance costs the cost rate on the total bought and sold. `daily` is the old idealised blend and is kept as `PlanBacktest.dailyRestored`. The plan backtest, projection sample, allocation preview, optimizer-reported metrics (baselines and out-of-sample included), `suggestPlan` and `fitCandidate` all use the rule; the optimizer's weight search still scores daily-restored mean and covariance estimates, which its notes say. One strategy gives the same result under every rule and `none` equals buy-and-hold of the starting split (tested).

**Out-of-sample check for proposals.** `suggestPlan` runs its weight search twice: on all history (the proposal) and on the first 60% (when both parts have at least a year). The early-fit weights, an equal split and each single sleeve are then measured on the remaining 40%; `oosVerdict` calls the result clearly worse when the early-fit weights break the fall limit later while an equal split does not, or trail the equal split's Sharpe by more than 0.15, says "a little worse, within noise" for smaller shortfalls, and adds a caution note when clearly worse. `Suggestion.outOfSample` carries the split date, weights, the three test-period results and the sentence shown in the proposal panel (and in the Copilot card, which reuses it).

**Results since a trade.** `quant/sinceTrade.ts`: `entryDay` gives the first close a follower could trade at (an SEC filing accepted before 20:00 UTC enters that day, later the next trading day; House reports and ARK trades the next trading day after their date; 13F rows have no public date and are skipped); `sinceTrade` measures each buy or sell from that close to the latest close and against SPY over the same days (`hit` is a buy that beat SPY or a sale of a stock that then trailed it) and summarises average excess and hit rate. `loadBars` in `dataSource.ts` loads one ticker's cleaned closes without aligning it to others (so a recent listing does not cut the window) through the same cache. `PERS` runs one query per persona over its newest 60 trades with tickers, four price downloads at a time.

**Copy-testing funds and insiders.** Funds: `fetchForm13F(cik, 8)` returns about seven quarters; `holdingsByPeriod` (now exported) groups them; `lib/figi.ts` maps CUSIPs to tickers through the `/figi` proxy to OpenFIGI (no key: 10 codes a request; codes starting with a letter are CINS, sent as `ID_CINS`; only US listings are asked for; share classes become `BRK-B`, `HEI-A`; cached by code). `fundSteps` holds each quarter's 25 largest priced holdings by value, renormalised, from the 45-day filing deadline (`filed`) or the quarter end (`traded`, the impossible comparison), and reports the share of reported value held; `runFundCopy` runs both over one window and lists as left out only holdings that would have made a quarter's top list. Insiders and House members: `copyEvents` now acts at `actDay`, the first close after a filing became public (an SEC acceptance after 20:00 UTC moves to the next day). `loadDatasetFrom` builds the copy dataset without letting a later listing shorten the window: tickers whose history starts after the window are left out and reported, and failed downloads are retried once. Checked live: copying Buffett's 13F held 36 stocks covering 99% of reported value, and waiting for each filing deadline cost $591 on $10,000 against holding from quarter end.

**Alerts.** `components/PersonaWatcher.tsx` is mounted once in `App` and runs on every screen: with `personaStore.alerts` on, it polls each followed persona's live SEC feed every ten minutes (`refetchIntervalInBackground`) through the same query keys as the Personas screen, so nothing is fetched twice. `quant/alerts.ts` `newAlerts` picks filings accepted after `seen[persona]` that contain a purchase, a sale or a stake report and are not in `notified`, one per filing; `batchNotifications` shows up to four and one more that counts the rest; `titleWithCount` sets "(N) StockHub" from the same rule. A persona never looked at gets its baseline instead of an alert, muted personas are skipped, and notified keys are kept (last 500). Notifications need the browser's permission, asked when alerts are turned on; without it only the title count shows. House reports and ARK's daily trades are not alerted.

**End-to-end tests.** `app/playwright.config.ts` starts the dev server on port 5179 (with a placeholder SEC contact so the live-filings code path is on) and runs `app/e2e/*.e2e.ts` (the suffix keeps Vitest from picking them up). `e2e/backends.ts` intercepts `/api`, `/rss`, `/sec`, `/clerk`, `/ark-api`, `/ark-assets`, `/figi`, `/ibkr` and `/llm` in the page and answers from `src/quant/fixtures` and seeded random-walk prices, so no request leaves the browser. The CI workflow's `e2e` job installs Playwright's Chromium and uploads the HTML report on failure.
